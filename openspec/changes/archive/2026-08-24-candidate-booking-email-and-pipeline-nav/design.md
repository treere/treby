## Context

Current state:

- The route `live "/schedule/:application_id", ScheduleLive.Index` exists (`router.ex:45`) but **nothing navigates to it**. The candidate detail page lists applications but has no "Schedule Interview" action. So the manual-booking page is effectively unreachable without typing the URL.
- `ScheduleLive.Index` (`schedule_live/index.ex`) already implements interviewer selection, slot computation (`Availability.compute_slots/2`), manual booking (`Calendar.create_event_with_meet/3` + `Interviews.schedule_interview/1`), and a "Generate Booking Link" button that prints a **relative** link (`schedule_live/index.ex:325`).
- `Interviews.schedule_interview/1` already moves the application to the Interview stage, sends confirmation emails to candidate and interviewer (`SchedulingEmail.interview_scheduled_candidate/5`, `...interviewer/5`), and logs the event. This part is done and tested — the gap is reachability.
- Booking tokens are generated by `Interviews.generate_booking_token/1` (7-day expiry, single-use) and consumed by `use_booking_token/1`; `interviewer_id` is optional in the schema (`booking_token.ex:23`), so a booking link can exist without an interviewer.
- There is a standalone Pipeline landing page `PipelineLive` (`/app/pipeline`, `pipeline_live/pipeline_live.ex`) that just lists jobs — duplicating the Jobs page. Nav links to it exist in desktop (`layouts.ex:66-71`) and mobile drawer (`layouts.ex:175-180`). `PipelineLive.Index` (`/app/pipeline/:job_id`) is the real Kanban board and is already linked from Jobs (`jobs_live/index.ex:177`, `jobs_live/show.ex:56`).
- Pipeline candidate cards render name/email/badges but the card is not a link to the candidate (`pipeline_live/index.ex:165-223`). Cards are draggable via the `Sortable` phx-hook.
- Absolute URLs for emails are built with `TrebyWeb.Endpoint.url()` (see `jobs_live/show.ex:44`).

## Goals / Non-Goals

**Goals:**

- Make the scheduling page reachable from the candidate detail page (one "Schedule Interview" action per application).
- Allow recruiters to email a candidate a self-scheduling booking link from the scheduling page, reusing the existing booking-token machinery with an absolute URL.
- Keep the manual booking flow and its existing candidate-confirmation email intact and covered by tests.
- Remove the standalone `/app/pipeline` landing page, its nav links (desktop + mobile), and the module, so pipeline boards are reachable only per job.
- Make pipeline candidate cards link to the candidate detail page without breaking drag-and-drop.

**Non-Goals:**

- No new scheduling channels (e.g., candidate-side "request a time" UI).
- No changes to slot computation, calendar integration, or availability rules.
- No new database schema changes — the existing `booking_tokens` and `interview_events` tables are sufficient.
- No changes to the interview scorecard or cancellation flows.

## Decisions

**1. Reach scheduling from the candidate detail page with one "Schedule Interview" action per application.**
In `candidates_live/show.ex`, in the Applications section (`show.ex:322-378`), add a "Schedule Interview" link per application next to "View Resume"/"Add Note" pointing to `/app/schedule/:application_id`. Rationale: the candidate page already groups applications with their job/status, which is the natural place to start scheduling. Alternative (a button on the pipeline card) was considered but rejected because pipeline cards will now navigate to candidate details (decision 4) and scheduling needs an application context the candidate page provides cleanly.

**2. Add an "Email booking link" action that reuses `Interviews.generate_booking_token/1` and emails an absolute URL.**
- Add `Interviews.booking_link_for/1` (or reuse inline logic in `ScheduleLive.Index`) that generates the token and returns the absolute URL: `TrebyWeb.Endpoint.url() <> "/#{slug}/schedule/#{token.token}"`.
- Add `SchedulingEmail.booking_link_candidate/4` (candidate, job, tenant, link) mirroring the style of the existing `SchedulingEmail` functions (HTML + text body, from `{"Treby", "noreply@treby.app"}`).
- In `schedule_live/index.ex`, add an "Email Booking Link" button next to "Generate Booking Link"; on click, generate the token (reusing `generate_booking_token/1`), build the absolute URL, deliver the email via `Treby.Mailer.deliver/1`, and show the link in the existing `@booking_link` box + a success flash.
- Rationale: reuses the proven booking-token flow (7-day expiry, single-use, optional interviewer), keeps emails in the existing `SchedulingEmail` module, and matches how `jobs_live/show.ex` builds absolute URLs. Alternative (a dedicated `Interviews.email_booking_link/1` context function) is viable; the change will put the email-sending in the LiveView handler and the URL construction in the `Interviews` context so it is testable in isolation.

**3. Manual booking page already sends confirmation emails; keep behavior, add tests.**
No changes to `Interviews.schedule_interview/1` or `SchedulingEmail.interview_scheduled_candidate/5` are required. The change adds reachability (decision 1) and ensures a LiveView test covers "schedule from candidate page → confirmation email sent".

**4. Remove the standalone Pipeline page and its nav entries.**
- Delete route `live "/pipeline", PipelineLive` from `router.ex` (keep `live "/pipeline/:job_id", PipelineLive.Index`).
- Delete `pipeline_live/pipeline_live.ex` module.
- Remove the desktop Pipeline nav link (`layouts.ex:66-71`) and the mobile drawer Pipeline link (`layouts.ex:175-180`).
- Rationale: the landing page duplicates Jobs; Jobs already links to each job's board. Removing the route makes the dead page unreachable and reduces nav clutter. This is a **breaking** removal for anyone relying on `/app/pipeline`, which is acceptable per the user's request.

**5. Make pipeline candidate cards link to candidate details without breaking drag-and-drop.**
Wrap the candidate name (and/or a "View" affordance) in a `<.link navigate={~p"/app/candidates/#{application.candidate_id}">` on each card (`pipeline_live/index.ex:184-198`). Keep the card's root `div` as the drag handle (`Sortable` hook operates on `#application-*`); the inner link is a separate element, so click-to-navigate and drag-to-move coexist. Rationale: simplest non-invasive approach; the `Sortable` hook triggers on drag, while a normal link handles click. Alternative (whole-card click with JS to distinguish drag vs click) was rejected as more fragile.

## Risks / Trade-offs

- **Booking link without interviewer shows no slots** → the booking page already handles `interviewer == nil` by showing an empty-slot state (`scheduling_live/booking.ex:26-28`); acceptable since the recruiter chooses whether to attach an interviewer. Design the email action to require a selected interviewer when one is expected, or document the empty-state UX.
- **Absolute URL uses `TrebyWeb.Endpoint.url()` which reflects config** → in production the configured URL must be correct; matches the existing pattern in `jobs_live/show.ex:44`. No new risk introduced.
- **Drag-and-drop vs click conflict on pipeline cards** → mitigated by keeping the link as a nested element and the card root as the drag target; will be verified in the browser and with the existing `Sortable` behavior.
- **Removing `/app/pipeline` could break bookmarks/links** → acceptable per requirement; the Jobs page remains the entry point. Checked that no in-app links or tests target `/app/pipeline` (only `/app/pipeline/:job_id`).
- **Email delivery failure** → wrap `Mailer.deliver` in the same try/rescue pattern used elsewhere (`careers_live/apply.ex:184-190`) so a delivery error surfaces as a flash, not a crash.

## Migration Plan

1. Add the booking-link email template and the URL helper (independently testable).
2. Add "Email Booking Link" action in `ScheduleLive.Index`.
3. Add "Schedule Interview" action per application on the candidate detail page.
4. Remove the standalone Pipeline route, module, and nav links.
5. Make pipeline candidate cards link to candidate details.
6. Add/update tests; run `mix precommit`.
7. Regenerate docs-site screenshots (`node scripts/screenshots.mjs`) and update the relevant `site/features/` pages.

Rollback: revert the router/nav/module deletion for the pipeline landing page; booking email changes are additive and can be reverted individually.
